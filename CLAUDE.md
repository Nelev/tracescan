# TraceScan

Multi-agent LLM failure triage (AI Engineering capstone). It reads an LLM app's traces, clusters the failures, diagnoses each cluster, and drafts GitHub issues plus regression tests for a human to approve. First target app: Medas, a clinician-facing RAG assistant.

## Project state

Building the MVP (see `PLAN.md` for what is done). Monorepo with `backend/` (Python, FastAPI) and `frontend/` (Next.js, a single run-console page), same layout as the `coa-agent` project. The code lives in two backend packages: `backend/agent/` (the graph) and `backend/trace_store/` (trace contracts, reader and MCP server). There is no `tracescan/` package. **Medas itself is instrumented in its own repo** (`medas-api/tracing/` in `Nelev/medas`, merged, and checked with a real signed-in request): a LangChain callback handler makes one trace per agent run (`invoke_agent medas`, `chat <model>`, `execute_tool <tool>`, `retrieval record_chunks` with `retrieval.hits`), with no prompt, answer or record text on any span, and exports it over OTLP/HTTP when `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` points at this collector (`http://localhost:<port>/v1/traces`). A tool that reports a failure to the model without raising is a span with status error and `error.type` `ToolReportedError`. Medas's API and UI default to ports 8000 and 3000 (Clerk expects the UI on 3000) and its Postgres to 5433, the same as here. To run both, run TraceScan on 8010 and 3010 (the `backend-8010` and `frontend-3010` launch entries; build the frontend with `BACKEND_URL=http://localhost:8010` first), point Medas's `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` at `http://localhost:8010/v1/traces`, and give Medas's database another port through `DATABASE_PORT` in `medas-api/.env`. | `backend/runs/` | The runs module (`runs/service.py`, import from `runs`): the only code that knows a run is a graph thread. `Runs(graph, context, open_traces, store)` is built once at startup with the run-independent `TraceContext` (embedder, model, `dry_run`, `out_dir`), whose `traces` it replaces for each run segment (an open session to start, `ClosedTraces` to review), and hides the `thread_id`, the config, the `TraceContext` and the trace session. `start(target_app, since, until, user)` is an async context manager that opens one trace session and the v3 stream on a fresh thread and yields a `StartedRun` (`run_id`, `events`: `Progress`\*, then one `Ended(status)` or `Failed`); leaving the context aborts the run, so a run is durable only once it waits for review. `status(run_id)` reads the checkpoint into a `RunStatus` (`status` of `in_progress`, `review_required` or `completed`, a `RunSummary` of counts plus `actions_log`, and the proposals); `failed` and `aborted` come from the run store, whose word is final for them (the checkpoint of a run cut short cannot tell, and between the clustering and the diagnose branches it even reads as ended); a run with a row but no checkpoint yet gets its status from the row. `list(limit)` returns the store's `RunRecord`s, newest first. `review(run_id, decisions, reviewer)` needs exactly one decision per proposal and resumes the graph with `Command(resume=...)` inside the store's `reviewing(...)` block, opening no trace session (`ClosedTraces`). That block is one database transaction holding a row lock on the run (`SELECT ... FOR UPDATE SKIP LOCKED`): a second review, in any process, skips the locked row and gets `NotClaimable` (a `409`), and the decisions and the run's new status (set by the `finish` the block yields) are committed together, or rolled back together when the resume fails or the process dies, so no status says "being reviewed" and none can be left behind. The cost: one pooled connection is held for the length of the resume (short while `apply_actions` is a dry run; revisit with real writers), and a failure after the graph has applied the actions but before the commit loses the record of that review. A paused run with no row (from before the table) is recorded at its review, with no starter: only when the run is not claimable and the row is missing. The precedence between the two records is the pure `_resolve(snapshot, record)`. **The run store** (`runs/store.py`): the `RunStore` protocol (`create_run`, which leaves an existing run alone, `set_status`, the `reviewing` context manager, `get_run`, `list_runs`), `PostgresRunStore` on SQLAlchemy Core (it also has `reviews(run_id)`, which only the tests read so far), and the `InMemoryRunStore` test double in `tests/fakes.py`; `tests/test_run_store.py` runs the same tests on both (Postgres only with `TEST_DATABASE_URL`, through the `postgres_url` fixture in `conftest.py`, which migrates the database; the store fixture truncates the three tables). Status writes after the run has started are best effort (`_mark`, logged by type name): the checkpoint drives the run, the row is the index. Leaving `start` early records `aborted` under a shielded cancel scope. `Runs` raises `RunFailed`, `RunNotFound`, `NotWaitingForReview` (also for a second review while the first is being applied) and `IncompleteDecisions` (`missing`, `unknown` cluster ids), none of which carries state or an underlying message. | `backend/api/runs.py`, `backend/api/schemas.py` | HTTP and SSE over `app.state.runs`, nothing more. `schemas.py` holds `RunRequest`, `ReviewRequest` (`decisions`: cluster id to `approve` or `reject`), and `ReviewResponse` (`status`, `summary`). Who starts or reviews a run is the `_user` dependency: the `X-User-Name` header, at most 80 characters, `local` without one; it is recorded, not verified (there is no login). There is no sync `POST /v1/runs` any more (it answers `405`). `POST /v1/runs/stream` (`target_app`, optional `since`/`until`) is the only way to start a run and streams it as server-sent events (FastAPI's native `fastapi.sse`, no extra dependency): `run_started {run_id}`, `progress` events from `agent.progress`, one `proposal` event per drafted proposal (the full `Proposal`, issue text included, validated against the schema by the runs module; sent after the last `progress`, none for a failed run; the Raw events tab lists them, the console draws only their `ui_spec`), and, right behind each message except `run_failed`, a `ui_spec {event, spec}`: the UI spec the small model wrote for it (a message whose call failed, was too slow, or was past `MAX_UI_CALLS_PER_RUN` has none), then the last message: `review_required` (the run waits at the review; it carries the summary, and the proposals to decide are the `proposal` events before it), `run_completed` (the run ended with nothing to review: no failures or no clusters; the same summary), either one followed by its own spec (so the frontend must keep reading until the stream closes, which it does) or `run_failed {}` with no detail, since the status is already 200 once the stream opens. The spec is one plain-JSON call per message on `app.state.ui_spec_model` (`build_ui_spec_model()`, `UI_SPEC_MODEL`, default `anthropic/claude-haiku-5.5`), from `api/ui_spec.py` and the prompt `api/ui_prompt.md`, awaited in the stream generator one after another (no queue, no tasks: a message is sent first and its own call never holds it back, but the next message waits for the call, so a run takes about `UI_CALL_TIMEOUT_S` at worst per message longer; a client that leaves cancels the request and with it the call), `UI_CALL_TIMEOUT_S` each. The backend knows nothing of json-render: it parses the reply as a JSON object and sends it as it is (no registry, no props check, no retry, no fallback), and the frontend is what checks and draws it. The prompt does carry the catalog in words, as plain text the frontend wrote: `api/ui_catalog.md` (one row per component: use, props with their allowed values and which are required, whether it takes children; about 7,000 characters, written by `npm run export:ui-prompt` in `frontend/` from `describeCatalog()` in `frontend/lib/ui-catalog-prompt.ts`; a frontend test fails when it is out of date) replaces `{{catalog}}` in `api/ui_prompt.md`, which also tells the model to send literal values only and to prefer display components. The model sees the message as it is: progress and lifecycle messages hold ids and counts, a `proposal` holds the diagnoser's prose (possibly clinical text) and the model copies its values with nothing checking the copy; spend is not counted yet; a failure is logged by exception type only. It forwards only `progress_events(stream)`, never raw stream events. The `TraceClient` and the run stream are owned by the `_open_run` dependency, not the generator: FastAPI never closes a generator that is suspended at a `yield` when the client disconnects, but it does unwind dependencies, so the run is aborted and the trace session released at once (tested with a stalled client, without `gc.collect()`). A trace session that cannot open is a plain `502` before the stream starts; a failure after that is a `run_failed` event. The per-run cap on UI spec calls is `UiSpecs` in `api/ui_spec.py`, one per stream. API tests set `app.state.graph` in the `client` fixture because `ASGITransport` skips the lifespan, and give the app its runs module with `use_runs(traces, model, open_traces)` in `tests/test_api.py` (the shared `fake_context`: a `HashingEmbedder`, so tests never download the model, and a fake chat model; plus a fake trace session). The `out_dir` fixture changes the working directory to `tmp_path`, so the default `out` lands there and no test writes into `backend/out`; nothing is patched with `monkeypatch` except the UI call cap. Shared fakes are in `tests/fakes.py` |
| `backend/api/traces.py` | The trace collector. `POST /v1/traces` takes an OTLP trace export as uncompressed binary protobuf (`415` for another content type, `400` for a body that is not an export), turns it into rows with the pure `decode(body)` (ids as hex, status as `unset`/`ok`/`error`, attributes as plain JSON: scalars and arrays, anything else null; spans whose `service.name` is not in `ALLOWED_APPS` are left out silently) and inserts them into `spans` (`status` checked against `SpanStatus`) with `store_spans(engine, rows)`, which returns how many were new, through `app.state.engine`, the application's role; a span already stored is left alone, so an exporter's retry changes nothing; a store failure is a `503` logged by exception type only. A failed trace is one with a root span whose lowest score in `scores` is at most the query's `max_score`: an error span alone does not make a trace failed, and a trace with no scores is not served. The failing span is the one the trace's lowest score blames (of several equally low scores, the first check by name); the `signature` is that span's name and its exception type or, without one, the check's name, no message; `min_score` is filled; **the scoring job** is `trace_store/scoring.py`: pure checks over a trace's span rows, each score a `(value, blamed span id)` with 0.0 bad and 1.0 fine, and every bad score blames a span: `request_failed` (every trace gets it; it blames `origin`, the deepest error span, the earliest of several), `tool_failures` (one pass over the tool calls giving `timeout`, `tool_schema_error` or `tool_error`; a failed call counts only when no later call of the same tool succeeded and its exception is not in `EXPECTED_ERRORS`, `medas.PatientNotFound`) and `empty_retrieval` (reads `retrieval.hits`). Its engine opens every transaction read-only, but no read-only role is created yet: point `TRACE_DATABASE_URL` at one when it exists. `tests/test_postgres_reader.py` covers it, including the whole path from a posted export to the MCP client (only with `TEST_DATABASE_URL`). `tests/test_traces_api.py` covers it (the store test only with `TEST_DATABASE_URL`). |

## Working rules

- Follow `PLAN.md` "Implementation plan" phase by phase. Tick a task's checkbox only when its "Done when" check passes.
- Keep the MVP tight. Do not start stretch tasks until the MVP gate (day 10) passes.
- Diagnoses are `unverified` in the MVP. Never drop a cluster because it did not reproduce.
- Cite evidence: every diagnosis must reference real trace ids and spans from its cluster.
- Medas traces may contain clinical content. Do not copy raw span attributes into issues, fixtures or logs without checking for personal data.

## Architecture (see PLAN.md for detail)

One LangGraph `StateGraph`:
`collect_traces → cluster_failures → diagnose_cluster ×N (parallel, via Send) → join_diagnoses → reproduce_failure ×N → match_known_issues → draft_proposals → human_review (interrupt) → apply_actions → END`

- `diagnose_cluster` is a plain structured-output call (`guarded` in `agent/model_guard.py`), not a `create_agent`: it needs no tools, and LangChain's `ModelRetryMiddleware` / `ModelCallLimitMiddleware` only run inside `create_agent`. Retries are the graph's loop (`diagnose_cluster` -> `join_diagnoses` -> `route_after_join` -> `diagnose_cluster`) with the budget in state, so they survive a resume. Each retry fetches the exemplar trees again (up to `MAX_EXEMPLARS` MCP calls, against `MAX_TOOL_CALLS` per run). If the diagnoser ever gets tools, move it to `create_agent(response_format=Diagnosis)` with a low recursion limit (~12). The outer pipeline stays a plain `StateGraph`.
- Parallel branches get small private inputs (`ClusterTask`, `ReproTask`), not the whole state. Fields filled by parallel branches use `Annotated[list[...], operator.add]`.
- Clustering is code (embeddings + HDBSCAN), not LLM calls. LLM calls happen per cluster, never per trace.
- Tracing stack is our own: Medas (OpenTelemetry, `gen_ai.*` attributes) → FastAPI OTLP collector → Postgres (`spans`, `scores`; a trace is the spans that share an id) → FastMCP read-only server → graph. Decided: no third-party observability platform (no Langfuse).

## Safety invariants

- Trace access is read-only: the MCP server (`search_failed_traces`, `get_trace_tree`, `get_span`) reads Postgres through a session whose transactions are read-only (a dedicated read-only role is planned, not created yet). The agent never touches the DB directly: `agent/` imports only `trace_store.models` and no DB drivers, and `backend/tests/test_boundaries.py` enforces it.
- MCP tool calls are limited where their arguments are declared and by one middleware. `search_failed_traces` serves only `ALLOWED_APPS` (checked in the tool body), and trace and span ids are typed `TraceId` (`models.py`, pattern `ID_PATTERN`), so pydantic rejects other shapes; give any new tool that takes an id the `TraceId` type. `TraceGuard` (`trace_store/guard.py`) wraps every call with a per-run budget (`MAX_TOOL_CALLS`; one server process is one graph run) and an audit log of tool, outcome and a hash of the arguments on stderr, never raw arguments, results or exception messages. Known limits: FastMCP's own "Invalid arguments for tool" warning repeats a rejected id or query on stderr, outside the guard's control; `get_trace_tree` and `get_span` take only ids, and the Postgres reader scopes them to `ALLOWED_APPS`. `get_span` is served but the agent does not call it yet.
- All writes (GitHub, eval dataset, known-issues store) happen only in `apply_actions`, only for human-approved proposals.
- `dry_run` defaults to `True` and is set by the server only (`DRY_RUN`), never by a request. Dry run writes `out/issues/<cluster>.md` and appends regression cases to `out/regression_cases.jsonl`, and nothing else (`out/` is `backend/out` when the app runs from `backend/`; it is gitignored and can hold the diagnoser's prose). Real writes do not exist yet: `DRY_RUN` off is refused at startup, and `apply_actions` refuses it too.
- The known-issues store is written only after an approved action, so rejected proposals never become "known".

## Commands

Backend commands run from `backend/`. This project uses `uv`, not `pip` (and `python3 -m venv` fails on this machine because `ensurepip` is missing). Create the virtualenv and install dependencies:

```bash
cd backend && uv sync
```

Run the FastAPI app (docs at `/docs`):

```bash
cd backend && uv run uvicorn main:app --reload
```

The app needs `DATABASE_URL` (for example `postgresql://user:pass@127.0.0.1:5432/tracescan`; `docker compose up -d` at the repo root starts one on port 5433) to checkpoint run state into Postgres and to record runs, and `TRACE_DATABASE_URL` (the same database; where each run's trace server reads spans and scores, meant for a read-only role). It fails at startup without either, or before the migration has run:

```bash
cd backend && uv run --env-file .env alembic upgrade head
```

After changing `db/models.py`, write the migration with `uv run --env-file .env alembic revision --autogenerate -m "..."` and read it before committing. To also run the Postgres test, set `TEST_DATABASE_URL`; the docker command is at the top of `backend/tests/test_persistence.py`.

`DRY_RUN` is optional and on by default; the app refuses to start with it off (see the safety invariants).

The diagnoser calls a model through OpenRouter: the app also fails at startup without `OPENROUTER_API_KEY`; optionally set `UI_SPEC_MODEL` (the small model that writes the UI spec of each streamed message; default `anthropic/claude-haiku-5.5` in `agent/const.py`, built into `app.state.ui_spec_model`) and `DIAGNOSER_MODEL` (an OpenRouter slug such as `anthropic/claude-sonnet-5-5`; default in `agent/const.py`). Tests never call a model. `langchain-openrouter` pulls in the `openrouter` SDK, which caps `pydantic<2.13`, so pydantic sits at 2.12 until that cap is lifted.

Frontend commands run from `frontend/` (install with `npm install`):

```bash
cd frontend && npm run dev
```

The UI needs the backend running too; if ports 3000 or 8000 are taken, start the backend with `--port 8010` and the frontend with `BACKEND_URL=http://localhost:8010 npm run dev -- --port 3010`.

```bash
cd backend && uv run ruff check . && uv run ruff format --check . && uv run pytest
```

## Conventions

- Python, Pydantic models for all structured output and state. Store plain dicts in state, or register the models module with the checkpoint serializer, to avoid the LangGraph serialization warning.
- Layout: `backend/agent/` (graph, `mcp_client.py`, `nodes/`), `backend/trace_store/` (contracts, Postgres reader, scoring job, MCP server) and `backend/eval/`; run modules from `backend/`, e.g. `uv run --env-file .env python -m eval.run`. Do not name a package `mcp/`: it would shadow the official `mcp` package that FastMCP imports; Next.js UI in `frontend/`.
- Failure categories: `retrieval_miss`, `tool_schema_error`, `context_overflow`, `prompt_regression`, `model_quality`, `infra_error`, plus MAST top-level `system_design`, `inter_agent_misalignment`, `task_verification`, and `unknown`.
- Frontend design system lives in `frontend/app/globals.css` (see the comment block there): dark navy surfaces with one electric blue accent (`primary`), and five status colors used for status only: `info` (under way; a lighter blue than `primary`), `warning` (waiting for a person, the only color that asks for action), `success`, `destructive` and `stopped` (cut short by choice: cancelled, aborted; an orange between amber and red); a status that is nothing (idle) is `muted-foreground`. Every status chip is `Chip` in `app/_components/chip.tsx` (one recipe per tone in `CHIP_TONE`, a mark per tone so color is never the only signal; the tone names are `StatusTone` in `lib/runs.ts`). Four type sizes via `type-h1` (24), `type-h2` (16), `type-h3` (14), `type-h4` (12 mono overline) plus `type-body` (14), and two weights (400, 500); do not use `text-xs`/`text-lg`/`text-3xl` or `font-semibold`. Desktop layout is a 12-column grid with body content on 9 columns (3/4).
- Eval = fault injection in Medas (6 seeded faults, varied inputs, healthy controls). Grade on the injected cause, not just the visible symptom.
- For parallel subagent work: contracts first, one owner per path, stubs for neighbouring features.
