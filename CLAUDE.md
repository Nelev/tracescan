# TraceScan

Multi-agent LLM failure triage (AI Engineering capstone). It reads an LLM app's traces, clusters the failures, diagnoses each cluster, and drafts GitHub issues plus regression tests for a human to approve. First target app: Medas, a clinician-facing RAG assistant.

## Project state

Building the MVP (see `PLAN.md` for what is done). Monorepo with `backend/` (Python, FastAPI) and `frontend/` (Next.js: runs, run pages and traces), same layout as the `coa-agent` project. The code lives in two backend packages: `backend/agent/` (the graph) and `backend/trace_store/` (trace contracts, reader and MCP server). There is no `tracescan/` package. **Medas itself is instrumented in its own repo** (`medas-api/tracing/` in `Nelev/medas`, merged, and checked with a real signed-in request): a LangChain callback handler makes one trace per agent run (`invoke_agent medas`, `chat <model>`, `execute_tool <tool>`, `retrieval record_chunks` with `retrieval.hits`), with no prompt, answer or record text on any span, and exports it over OTLP/HTTP when `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` points at this collector (`http://localhost:<port>/v1/traces`). A tool that reports a failure to the model without raising is a span with status error and `error.type` `ToolReportedError`. Medas's API and UI default to ports 8000 and 3000 (Clerk expects the UI on 3000) and its Postgres to 5433, the same as here. To run both, run TraceScan on 8010 and 3010 (the `backend-8010` and `frontend-3010` launch entries; build the frontend with `BACKEND_URL=http://localhost:8010` first), point Medas's `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` at `http://localhost:8010/v1/traces`, and give Medas's database another port through `DATABASE_PORT` in `medas-api/.env`. FOR UPDATE SKIP LOCKED`): a second review, in any process, skips the locked row and gets `NotClaimable` (a `409`), and the decisions and the run's new status (set by the `finish` the block yields) are committed together, or rolled back together when the resume fails or the process dies, so no status says "being reviewed" and none can be left behind. The cost: one pooled connection is held for the length of the resume (short while `apply_actions` is a dry run; revisit with real writers), and a failure after the graph has applied the actions but before the commit loses the record of that review. A run with no row cannot be reviewed (`409`). There is no sync `POST /v1/runs` any more (it answers `405`). `POST /v1/runs/stream` (`target_app`, optional `since`/`until`) is the only way to start a run and streams it as server-sent events (FastAPI's native `fastapi.sse`, no extra dependency): `run_started {run_id}`, `progress` events from `agent.progress`, one `proposal` event per drafted proposal (the full `Proposal`, issue text included, validated against the schema by the runs module; sent after the last `progress`, none for a failed run; the agent console's Raw events view lists them, the console draws only their `ui_spec`), and, right behind each message except `run_failed`, a `ui_spec {event, spec}`: the UI spec the small model wrote for it (a message whose call failed, was too slow, or was past `MAX_UI_CALLS_PER_RUN` has none), then the last message: `review_required` (the run waits at the review; it carries the summary, and the proposals to decide are the `proposal` events before it), `run_completed` (the run ended with nothing to review: no failures or no clusters; the same summary), either one followed by its own spec (so the frontend must keep reading until the stream closes, which it does) or `run_failed {}` with no detail, since the status is already 200 once the stream opens. The spec is one plain-JSON call per message on `app.state.ui_spec_model` (`build_ui_spec_model()`, `UI_SPEC_MODEL`, default `anthropic/claude-haiku-5.5`), from `api/ui_spec.py` and the prompt `api/ui_prompt.md`, awaited in the stream generator one after another (no queue, no tasks: a message is sent first and its own call never holds it back, but the next message waits for the call, so a run takes about `UI_CALL_TIMEOUT_S` at worst per message longer; a client that leaves cancels the request and with it the call), `UI_CALL_TIMEOUT_S` each. The backend knows nothing of json-render: it parses the reply as a JSON object and sends it as it is (no registry, no props check, no retry, no fallback), and the frontend is what checks and draws it. The prompt does carry the catalog in words, as plain text the frontend wrote: `api/ui_catalog.md` (one row per component: use, props with their allowed values and which are required, whether it takes children; about 7,000 characters, written by `npm run export:ui-prompt` in `frontend/` from `describeCatalog()` in `frontend/lib/ui-catalog-prompt.ts`; a frontend test fails when it is out of date) replaces `{{catalog}}` in `api/ui_prompt.md`, which also tells the model to send literal values only and to prefer display components. ## Working rules

- Follow `PLAN.md` "Implementation plan" phase by phase. Tick a task's checkbox only when its "Done when" check passes.
- Keep the MVP tight. Do not start stretch tasks until the MVP gate (day 10) passes.
- Diagnoses are `unverified` in the MVP. Never drop a cluster because it did not reproduce.
- Cite evidence: every diagnosis must reference real trace ids and spans from its cluster.
- Medas traces may contain clinical content. Do not copy raw span attributes into issues, fixtures or logs without checking for personal data.

## Architecture (see PLAN.md for detail)

One LangGraph `StateGraph`:
`collect_traces → score_trace ×T (parallel, via Send) → join_scores → cluster_failures → diagnose_cluster ×N (parallel, via Send) → draft_proposals → human_review (interrupt) → apply_actions → END` (planned, not in the graph yet: `reproduce_failure ×N → match_known_issues` before `draft_proposals`)

- `diagnose_cluster` is a plain structured-output call (`guarded` in `agent/model_guard.py`), not a `create_agent`: it needs no tools, and LangChain's `ModelRetryMiddleware` / `ModelCallLimitMiddleware` only run inside `create_agent`. Retries are a loop inside the node with the budget in a local `Spent`, not a graph loop: a run is durable only once it waits for review, so checkpointing retry state would buy nothing. The exemplar trees are fetched once per cluster. If the diagnoser ever gets tools, move it to `create_agent(response_format=Diagnosis)` with a low recursion limit (~12). The outer pipeline stays a plain `StateGraph`.
- Parallel branches get small private inputs (`ClusterTask`, `ReproTask`), not the whole state. Fields filled by parallel branches use `Annotated[list[...], operator.add]`.
- Clustering is code (embeddings + HDBSCAN), not LLM calls. The one per-trace LLM call is the trace judge (`score_trace`, up to `MAX_JUDGED_TRACES` per run), which decides which traces failed; every other LLM call is per cluster.
- Tracing stack is our own: Medas (OpenTelemetry, `gen_ai.*` attributes) → FastAPI OTLP collector → Postgres (`spans`, `scores`; a trace is the spans that share an id) → FastMCP read-only server → graph. Decided: no third-party observability platform (no Langfuse).

## Safety invariants

- Identity comes only from a verified Clerk session token (`backend/auth/`), never from a request field or header. Every API route needs one except `GET /health` and the collector `POST /v1/traces`, which has no credential yet (localhost and synthetic traffic only).
- Trace access is read-only: the MCP server (`search_traces`, `get_trace_tree`, `get_span`) reads Postgres through a session whose transactions are read-only (a dedicated read-only role is planned, not created yet). The agent never touches the DB directly: `agent/` imports only `trace_store.models` and no DB drivers, and `backend/tests/test_boundaries.py` enforces it.
- MCP tool calls are limited where their arguments are declared and by one middleware. `search_traces` serves only `ALLOWED_APPS` (checked in the tool body), and trace and span ids are typed `TraceId` (`models.py`, pattern `ID_PATTERN`), so pydantic rejects other shapes; give any new tool that takes an id the `TraceId` type. `TraceGuard` (`trace_store/guard.py`) wraps every call with a per-run budget (`MAX_TOOL_CALLS`; one server process is one graph run) and an audit log of tool, outcome and a hash of the arguments on stderr, never raw arguments, results or exception messages. Known limits: FastMCP's own "Invalid arguments for tool" warning repeats a rejected id or query on stderr, outside the guard's control; `get_trace_tree` and `get_span` take only ids, and the Postgres reader scopes them to `ALLOWED_APPS`. `get_span` is served but the agent does not call it yet.
- All writes (GitHub, eval dataset, known-issues store) happen only in `apply_actions`, only for human-approved proposals. The two exceptions are the healthy-span store (`runs/healthy.py`) and the judge's scores (`runs/scores.py`), both written after every run without review: they hold only `step_text` (names, error types, bucketed numbers) and ids and scores, and stay in the application's database.
- `dry_run` defaults to `True` and is set by the server only (`DRY_RUN`), never by a request. Dry run writes `out/issues/<cluster>.md` and appends regression cases to `out/regression_cases.jsonl`, and nothing else (`out/` is `backend/out` when the app runs from `backend/`; it is gitignored and can hold the diagnoser's prose). Real writes do not exist yet: `DRY_RUN` off is refused at startup, and `apply_actions` refuses it too.
- The known-issues store is written only after an approved action, so rejected proposals never become "known".

## Commands

Backend commands run from `backend/`. This project uses `uv`, not `pip` (and `python3 -m venv` fails on this machine because `ensurepip` is missing). Create the virtualenv and install dependencies:

```bash
cd backend && uv sync
```

Run the FastAPI app (docs at `/docs`):

```bash
cd backend && uv run uvicorn main:app --reload
```

The app needs `DATABASE_URL` (for example `postgresql://user:pass@127.0.0.1:5432/tracescan`; `docker compose up -d` at the repo root starts one on port 5433) to checkpoint run state into Postgres and to record runs, and `TRACE_DATABASE_URL` (the same database; where each run's trace server reads spans and scores, meant for a read-only role). It fails at startup without either, or before the migration has run:

```bash
cd backend && uv run --env-file .env alembic upgrade head
```

After changing `db/models.py`, write the migration with `uv run --env-file .env alembic revision --autogenerate -m "..."` and read it before committing. To also run the Postgres test, set `TEST_DATABASE_URL`; the docker command is at the top of `backend/tests/test_persistence.py`.

`DRY_RUN` is optional and on by default; the app refuses to start with it off (see the safety invariants).

The app also fails at startup without `CLERK_SECRET_KEY` (the TraceScan Clerk application's; see `backend/.env.example` for `CLERK_JWT_KEY` and `CLERK_AUTHORIZED_PARTIES`). The diagnoser calls a model through OpenRouter: the app also fails at startup without `OPENROUTER_API_KEY`; optionally set `UI_SPEC_MODEL` (the small model that writes the UI spec of each streamed message; default `anthropic/claude-haiku-5.5` in `agent/const.py`, built into `app.state.ui_spec_model`) `DIAGNOSER_MODEL` (an OpenRouter slug such as `anthropic/claude-sonnet-5-5`; default in `agent/const.py`) and `TRACE_JUDGE_MODEL` (the trace judge, one call per trace in a run's window; default `anthropic/claude-haiku-5.5`, `DEFAULT_TRACE_JUDGE_MODEL` in `agent/const.py`; not `JUDGE_MODEL`, which is the eval's grader). Tests never call a model. `langchain-openrouter` pulls in the `openrouter` SDK, which caps `pydantic<2.13`, so pydantic sits at 2.12 until that cap is lifted.

Frontend commands run from `frontend/` (install with `npm install`):

```bash
cd frontend && npm run dev
```

`npm run build` builds, `npm run lint` runs Biome, `npx tsc --noEmit` typechecks, and `npm test` runs the unit tests of the pure modules in `lib/` with Node's built-in runner (no dependency; those modules import each other with `.ts` extensions, which `allowImportingTsExtensions` allows, so `node --test` can load them). The UI needs the backend running too; if ports 3000 or 8000 are taken, start the backend with `--port 8010` and the frontend with `BACKEND_URL=http://localhost:8010 npm run dev -- --port 3010`.

Backend checks (run from `backend/`; the Backend CI workflow runs all four). Pyright reads `pyrightconfig.json` at the repo root, the same config the editor uses, hence `-p ..`:

```bash
cd backend && uv run ruff check . && uv run ruff format --check . && uv run pyright -p .. && uv run pytest
```

`RUN_SLOW=1 uv run pytest -k fastembed` repeats the clustering check with the real embedding model; setup, cache location and offline use are in the README. Without `RUN_SLOW` that test is skipped, so CI never downloads the model. CI never calls a model: the diagnoser on the real model is the eval below. CI does have a Postgres service and sets `TEST_DATABASE_URL`, so the tests of the trace path (collector, reader, trace browser, trace client, eval runner, run store, persistence) run there; locally they are skipped without it.

The eval on seeded traces (needs `DATABASE_URL`, `TRACE_DATABASE_URL` and `OPENROUTER_API_KEY`; about $0.08 a run): `uv run --env-file .env python -m eval.run`, then `uv run --env-file .env python -m eval.judge`, then `uv run python -m eval.metrics`. See the `backend/eval/` row.

`uv run ruff check --fix .` and `uv run ruff format .` fix what they report. Ruff is configured in `backend/pyproject.toml` (rules `E,F,I,UP,B`, line length 100).

Planned: a ruff pre-commit hook, `langgraph dev` for Studio (compile without a local checkpointer/store and point `langgraph.json` at the module's `graph`).

## Conventions

- Python, Pydantic models for all structured output and state. Store plain dicts in state, or register the models module with the checkpoint serializer, to avoid the LangGraph serialization warning.
- Layout: `backend/agent/` (graph, `mcp_client.py`, `nodes/`), `backend/trace_store/` (contracts, Postgres reader, MCP server) and `backend/eval/`; run modules from `backend/`, e.g. `uv run --env-file .env python -m eval.run`. Do not name a package `mcp/`: it would shadow the official `mcp` package that FastMCP imports; Next.js UI in `frontend/`.
- Failure categories: `retrieval_miss`, `tool_schema_error`, `context_overflow`, `prompt_regression`, `model_quality`, `infra_error`, plus MAST top-level `system_design`, `inter_agent_misalignment`, `task_verification`, and `unknown`.
- Frontend design system lives in `frontend/app/globals.css` (see the comment block there): Dark Mode (OLED), dark only: the app never draws a light theme whatever the system setting (`:root` is dark with `color-scheme: dark`, the `dark:` variant always applies, and `layout.tsx` exports a dark `viewport` so the browser's own chrome, form controls and scrollbars match). A true black page (`background`, `sidebar`), slate-tinted panels one step above it, text in a dimmed off-white (low white emission), one indigo accent, a near-white focus `ring`. A panel is `surface` (`card`, its own hairline `border`, no shadow: shadows do not show on black); what floats over content (menus, tooltips, the review bar) is `surface-raised` (`popover`, `elevation-2`: a faint light rim); the `shadow-*` scale maps to the `--elevation-*` tokens, and `shadow-glow` (`--glow-primary`) is the accent's soft glow, on a filled action under the pointer and on the active nav mark; `--radius` is 0.75rem (chips and badges are pills). `primary` is the one accent (actions, selection, the AI's marks, chart bars), and a filled action under the pointer is `primary-hover`; no gradients. What the agent wrote reads as a context card, `ai-context` (the `ai-surface` tint and a 2px `primary` left line): the agent console's messages (spaced by `--message-gap`, each revealed with a short fade under `motion-safe`) and the suggested fix. While a run streams the console shows `TypingDots` (`typing-dots.tsx`, the `typing-dot` utility, still under `prefers-reduced-motion`). Hairline `border` between regions and the strong `rule` line under table heads and chart axes, `hover` and `track` tokens for a pointed-at row and the empty part of a bar; links are underlined, not colored. Five status colors are used for status only and only on small marks (chips, icons, counts, a thin stripe), never as a large border or fill: `info` (under way), `warning` (waiting for a person, the only color that asks for action), `success`, `destructive` and `stopped` (cut short by choice: cancelled, aborted); a status that is nothing (idle) is `muted-foreground`. Every token keeps WCAG contrast on every surface (numbers in the `globals.css` comment): text 4.5:1, controls and focus 3:1; re-measure after changing a color. Code that reads a token's color (the 3D map paints one pixel) composites translucent tokens over `--background`. Every layer that floats takes a named z utility from `globals.css`, never a bare number: `z-sticky` (10: sticky table heads, the review bar, chart tooltips), `z-header` (20), `z-console` (30: the chat box, above the sticky parts and below popovers) and `z-overlay` (50: popovers and menus); a component that stacks its own parts inside an isolated box (the 3D map, the calendar) may use plain `z-0`/`z-10` there. Every status chip is `Chip` in `app/_components/chip.tsx` (one line always: a label that does not fit is cut with an ellipsis, in full on hover) (one recipe per tone in `CHIP_TONE`, a mark per tone so color is never the only signal; the tone names are `StatusTone` in `lib/runs.ts`). The root font size stays the browser's 16px (`type-body` is applied to `<body>`, not `<html>`, or every rem would shrink by 1/8); headings balance their lines and paragraphs and list items wrap `pretty`; no `transition-all` (buttons transition color, background, border, shadow and a 0.97 press scale); controls keep a 40px hit area (a small button widens its own with an `after:` pseudo-element). Four type sizes via `type-h1` (28), `type-h2` (16), `type-h3` (14), `type-h4` (12 uppercase overline) plus `type-body` (14), and three weights (400 body, 500 emphasis, 600 for h1 and h2); do not use `text-xs`/`text-lg`/`text-3xl` or `font-semibold`. Desktop layout is a 12-column grid with body content on 9 columns (3/4).
- Eval = fault injection in Medas (6 seeded faults, varied inputs, healthy controls). Grade on the injected cause, not just the visible symptom.
- For parallel subagent work: contracts first, one owner per path, stubs for neighbouring features.
