# TraceScan

Multi-agent LLM failure triage (AI Engineering capstone). It reads an LLM app's traces, clusters the failures, diagnoses each cluster, and drafts GitHub issues plus regression tests for a human to approve. First target app: Medas, a clinician-facing RAG assistant.

## Project state

Planning stage. Monorepo with `backend/` (Python, FastAPI) and `frontend/` (Next.js, a single run-console page), same layout as the `coa-agent` project. The code lives in two backend packages: `backend/agent/` (the graph) and `backend/trace_store/` (trace contracts, reader and MCP server). There is no `tracescan/` package. What exists:

The v3 protocol is experimental and `stream.output` is a method in 1.2.20. `diagnose_cluster` copies its model with `disable_streaming=True`, because under v3 LangChain would otherwise route the call through its token-streaming path, which a plain fake model does not implement), `nodes/collect_traces.py` (real `collect_traces`, reads the client from `runtime.context`), `nodes/cluster_failures.py` (real `cluster_failures`, runs the clustering off the event loop and writes `clusters` and `unclustered`; each unclustered id also becomes a one-trace cluster (`method` `isolated`, id numbered after the real clusters, built by `clustering.isolated_clusters`) so it is diagnosed like any other, with no cap yet), `nodes/diagnose_cluster.py` (real `diagnose_cluster`: takes a `ClusterTask`, fetches the exemplar span trees, and makes one `with_structured_output(Diagnosis)` call with `taxonomy.md` as the system prompt; it overwrites `cluster_id` from the task; every cited span must be a span of the exemplar trees it was shown: if not, the model is asked once more with the valid ids listed, and if it still cites spans it was not shown they are dropped, the confidence is capped at `UNSUPPORTED_CONFIDENCE_CAP`, and with no real citation left the cluster's own first failing span is cited. The stored dict gets `evidence_check` (`valid`, `corrected` or `unsupported`, never filled by the model); a cluster that fails, including a failing retry, is logged by exception type only and its id goes to `diagnosis_failures`. Each run is one attempt with a budget check before and after, against the cluster's `model_usage` entries in state, which the router puts in the `ClusterTask` (a node reached through `Send` sees only its payload, not the state). A transient model error with budget left, after a call made in this run, returns only the usage entry, so the cluster stays unfinished and the graph runs the node again after a doubling wait; without budget, or for any other error, it goes to `diagnosis_failures`. The evidence re-ask checks the same budget (earlier runs plus this one): when it is spent the diagnosis is kept as `unsupported`, not failed. Every run appends `{cluster_id, calls, tokens, cost_usd}` for itself to `model_usage`, so failed spend shows too), `nodes/apply_actions.py` and `actions.py` (real `apply_actions`, the graph's only writing node, a sync node with no model call: it takes the proposals whose decision is `approve` and, as a dry run, hands them to the pure `write_dry_run(proposals, out_dir)`, which writes `issues/<cluster_id>.md` (the title as a heading, then the issue body; a later run's `c0` replaces an earlier one's) and appends each regression case as one JSON line to `regression_cases.jsonl` (an undiagnosed proposal writes its issue only), and returns the `actions_log` with paths relative to `out_dir`. A cluster id that is not a safe file name (`[A-Za-z0-9_-]+`) raises before anything is written. With `dry_run` off the node raises `NotImplementedError` before any write, through `require_dry_run` in `actions.py`: the one place that says the real writers do not exist, which the app also calls at startup; per the design decision there is no writer seam, the node branches on `dry_run`), `nodes/draft_proposals.py` and `proposals.py` (real `draft_proposals`, no model call: pure `build_proposals(clusters, diagnoses)` renders the issue markdown with plain f-strings into one `Proposal` per cluster in cluster order, with a `RegressionCase` of ids only (exemplar traces and cited spans, no span text) for a diagnosed cluster; a cluster without a diagnosis gets a stub proposal (`diagnosed` False, no regression case), never dropped; `verification` is always `unverified` until the reproducer exists; an evidence check other than `valid` is flagged in the body; the issue prose is the model's own text, so human review is the gate against clinical content), `evidence.py` (the pure checks: `span_index`, `invalid_citations`, `keep_valid`, `retry_message`, `fallback_evidence`), `model_guard.py` (the budget and retry building blocks: `Spent` (calls, tokens, cost; `+`; `ok()` checks `MAX_MODEL_ATTEMPTS`, `MAX_CLUSTER_TOKENS` and `MAX_CLUSTER_COST_USD` in `const.py`, starting values), `spent_for(usage, cluster_id)` summing a cluster's `model_usage` entries from state, `retryable(exc)` (408, 429, 5xx, timeouts, dropped connections; the SDK raises its own errors with a `status_code`, not LangChain's `ModelError`; anything else is a bug and is not retried), `backoff_delay(calls)` and `guarded(ask, spent)`, one call made with `include_raw=True` so the raw message gives the tokens and the cost OpenRouter reports (`response_metadata["cost"]`, counted as 0 when absent)), `clustering.py` (pure `cluster_summaries(summaries, embedder)`; the README's clustering section explains the two stages), `embeddings.py` (`Embedder` protocol and the local `FastEmbedEmbedder`; the offline `HashingEmbedder` test double is in `tests/fakes.py`), `const.py` (clustering thresholds, tuned on the synthetic fixture with the real model), `state.py` (`TriageState`, with optional `since`/`until` window, `unclustered`, and the append-reducer fields `diagnoses`, `diagnosis_failures` and `model_usage` filled by the parallel branches), `schemas.py` (data contracts: the `Cluster` TypedDict (`cluster_id`, `trace_ids`, `signature`, `exemplar_trace_ids`, `method` of `hdbscan`, `step_error` or `isolated`), `FailureCategory`/`FAILURE_CATEGORIES`, `Decision` (`approve` or `reject`, what the reviewer answers per proposal), the `ClusterTask` input of a diagnose branch, the `Diagnosis` and `Evidence` Pydantic models the diagnoser returns, and the `SpanRef`, `RegressionCase` and `Proposal` models of a drafted proposal), `mcp_client.py` (`TraceClient`: async context manager holding one stdio session to the trace server for a graph run, typed `search_failed_traces` and `get_trace_tree`). | `backend/runs/` | The runs module (`runs/service.py`, import from `runs`): the only code that knows a run is a graph thread. `Runs(graph, context, open_traces, store)` is built once at startup with the run-independent `TraceContext` (embedder, model, `dry_run`, `out_dir`), whose `traces` it replaces for each run segment (an open session to start, `ClosedTraces` to review), and hides the `thread_id`, the config, the `TraceContext` and the trace session. `start(target_app, since, until, user)` is an async context manager that opens one trace session and the v3 stream on a fresh thread and yields a `StartedRun` (`run_id`, `events`: `Progress`\*, then one `Ended(status)` or `Failed`); leaving the context aborts the run, so a run is durable only once it waits for review. `status(run_id)` reads the checkpoint into a `RunStatus` (`status` of `in_progress`, `review_required` or `completed`, a `RunSummary` of counts plus `actions_log`, and the proposals); `failed` and `aborted` come from the run store, whose word is final for them (the checkpoint of a run cut short cannot tell, and between the clustering and the diagnose branches it even reads as ended); a run with a row but no checkpoint yet gets its status from the row. `list(limit)` returns the store's `RunRecord`s, newest first. `review(run_id, decisions, reviewer)` needs exactly one decision per proposal and resumes the graph with `Command(resume=...)` inside the store's `reviewing(...)` block, opening no trace session (`ClosedTraces`). That block is one database transaction holding a row lock on the run (`SELECT ... FOR UPDATE SKIP LOCKED`): a second review, in any process, skips the locked row and gets `NotClaimable` (a `409`), and the decisions and the run's new status (set by the `finish` the block yields) are committed together, or rolled back together when the resume fails or the process dies, so no status says "being reviewed" and none can be left behind. The cost: one pooled connection is held for the length of the resume (short while `apply_actions` is a dry run; revisit with real writers), and a failure after the graph has applied the actions but before the commit loses the record of that review. A paused run with no row (from before the table) is recorded at its review, with no starter: only when the run is not claimable and the row is missing. The precedence between the two records is the pure `_resolve(snapshot, record)`. **The run store** (`runs/store.py`): the `RunStore` protocol (`create_run`, which leaves an existing run alone, `set_status`, the `reviewing` context manager, `get_run`, `list_runs`), `PostgresRunStore` on SQLAlchemy Core (it also has `reviews(run_id)`, which only the tests read so far), and the `InMemoryRunStore` test double in `tests/fakes.py`; `tests/test_run_store.py` runs the same tests on both (Postgres only with `TEST_DATABASE_URL`, through the `postgres_url` fixture in `conftest.py`, which migrates the database; the store fixture truncates the three tables). Status writes after the run has started are best effort (`_mark`, logged by type name): the checkpoint drives the run, the row is the index. Leaving `start` early records `aborted` under a shielded cancel scope. `Runs` raises `RunFailed`, `RunNotFound`, `NotWaitingForReview` (also for a second review while the first is being applied) and `IncompleteDecisions` (`missing`, `unknown` cluster ids), none of which carries state or an underlying message. Callers never get raw graph state |
| `backend/api/runs.py`, `backend/api/schemas.py` | HTTP and SSE over `app.state.runs`, nothing more. `schemas.py` holds `RunRequest`, `ReviewRequest` (`decisions`: cluster id to `approve` or `reject`) and `ReviewResponse` (`status`, `summary`). No response carries raw state (it can hold clinical span data); checkpoints do hold state, so keep it to ids and signatures. `GET /v1/runs/{run_id}` returns the `RunStatus` (`404` for an unknown run, `422` for an id that is not a UUID). `POST /v1/runs/{run_id}/review` resumes a paused run and returns plain JSON, the status and the summary with its `actions_log`: `409` when the run is not waiting for review, `422` with `{missing, unknown}` when the decisions do not match the proposals, `502` when the resume fails. `GET /v1/runs` (`limit`, 1 to 200, default 50) lists the newest runs as `RunRecord`s: ids, the starter's name, status and counts, never state or proposals. Who starts or reviews a run is the `_user` dependency: the `X-User-Name` header, at most 80 characters, `local` without one; it is recorded, not verified (there is no login). There is no sync `POST /v1/runs` any more (it answers `405`). `POST /v1/runs/stream` (`target_app`, optional `since`/`until`) is the only way to start a run and streams it as server-sent events (FastAPI's native `fastapi.sse`, no extra dependency): `run_started {run_id}`, `progress` events from `agent.progress`, one `proposal` event per drafted proposal (the full `Proposal`, issue text included, validated against the schema by the runs module; sent after the last `progress`, none for a failed run; the Raw events tab lists them, the console draws only their `ui_spec`), and, right behind each message except `run_failed`, a `ui_spec {event, spec}`: the UI spec the small model wrote for it (a message whose call failed, was too slow, or was past `MAX_UI_CALLS_PER_RUN` has none), then the last message: `review_required` (the run waits at the review; it carries the summary, and the proposals to decide are the `proposal` events before it), `run_completed` (the run ended with nothing to review: no failures or no clusters; the same summary), either one followed by its own spec (so the frontend must keep reading until the stream closes, which it does) or `run_failed {}` with no detail, since the status is already 200 once the stream opens. The spec is one plain-JSON call per message on `app.state.ui_spec_model` (`build_ui_spec_model()`, `UI_SPEC_MODEL`, default `anthropic/claude-haiku-5.5`), from `api/ui_spec.py` and the prompt `api/ui_prompt.md`, awaited in the stream generator one after another (no queue, no tasks: a message is sent first and its own call never holds it back, but the next message waits for the call, so a run takes about `UI_CALL_TIMEOUT_S` at worst per message longer; a client that leaves cancels the request and with it the call), `UI_CALL_TIMEOUT_S` each. The backend knows nothing of json-render: it parses the reply as a JSON object and sends it as it is (no registry, no props check, no retry, no fallback), and the frontend is what checks and draws it. The prompt does carry the catalog in words, as plain text the frontend wrote: `api/ui_catalog.md` (one row per component: use, props with their allowed values and which are required, whether it takes children; about 7,000 characters, written by `npm run export:ui-prompt` in `frontend/` from `describeCatalog()` in `frontend/lib/ui-catalog-prompt.ts`; a frontend test fails when it is out of date) replaces `{{catalog}}` in `api/ui_prompt.md`, which also tells the model to send literal values only and to prefer display components. The model sees the message as it is: progress and lifecycle messages hold ids and counts, a `proposal` holds the diagnoser's prose (possibly clinical text) and the model copies its values with nothing checking the copy; spend is not counted yet; a failure is logged by exception type only. It forwards only `progress_events(stream)`, never raw stream events. The `TraceClient` and the run stream are owned by the `_open_run` dependency, not the generator: FastAPI never closes a generator that is suspended at a `yield` when the client disconnects, but it does unwind dependencies, so the run is aborted and the trace session released at once (tested with a stalled client, without `gc.collect()`). A trace session that cannot open is a plain `502` before the stream starts; a failure after that is a `run_failed` event. The per-run cap on UI spec calls is `UiSpecs` in `api/ui_spec.py`, one per stream. API tests set `app.state.graph` in the `client` fixture because `ASGITransport` skips the lifespan, and give the app its runs module with `use_runs(traces, model, open_traces)` in `tests/test_api.py` (the shared `fake_context`: a `HashingEmbedder`, so tests never download the model, and a fake chat model; plus a fake trace session). The `out_dir` fixture changes the working directory to `tmp_path`, so the default `out` lands there and no test writes into `backend/out`; nothing is patched with `monkeypatch` except the UI call cap. Shared fakes are in `tests/fakes.py` |

That chunk (json-render, zod, the components) is loaded with `next/dynamic` and starts loading when a run starts, so it is not in the first load. `components/ui/tabs.tsx` is written by hand on Base UI, not generated. `next.config.ts` rewrites `/api/:path*` to `${BACKEND_URL:-http://localhost:8000}/v1/:path*` (and `/api/health` to `/health`) because the backend has no CORS, and sets `compress: false`: Next's gzip buffers an event stream until the run ends (checked in `next dev` and `next start`; a `no-transform` header does not help). **Review** is `app/_components/review-pane.tsx` over the hook `use-review.ts`, mounted with the run id as `key`: this page's run while it waits, or a waiting run picked under Runs. A failed send keeps the decisions and says why (409, 422, 502, unreachable); a 2xx whose answer cannot be read (`RunError.unreadable`) counts as sent, not as a refusal; a run that does not wait is shown as it stands. Its tab panel is the only one kept mounted (`keepMounted`), so a look at another tab loses neither the decisions nor the outcome. ## Working rules

- Follow `PLAN.md` "Implementation plan" phase by phase. Tick a task's checkbox only when its "Done when" check passes.
- Keep the MVP tight. Do not start stretch tasks until the MVP gate (day 10) passes.
- Diagnoses are `unverified` in the MVP. Never drop a cluster because it did not reproduce.
- Cite evidence: every diagnosis must reference real trace ids and spans from its cluster.
- Medas traces may contain clinical content. Do not copy raw span attributes into issues, fixtures or logs without checking for personal data.

## Architecture (see PLAN.md for detail)

One LangGraph `StateGraph`:
`collect_traces → cluster_failures → diagnose_cluster ×N (parallel, via Send) → join_diagnoses → reproduce_failure ×N → match_known_issues → draft_proposals → human_review (interrupt) → apply_actions → END`

- `diagnose_cluster` is a plain structured-output call (`guarded` in `agent/model_guard.py`), not a `create_agent`: it needs no tools, and LangChain's `ModelRetryMiddleware` / `ModelCallLimitMiddleware` only run inside `create_agent`. Retries are the graph's loop (`diagnose_cluster` -> `join_diagnoses` -> `route_after_join` -> `diagnose_cluster`) with the budget in state, so they survive a resume. Each retry fetches the exemplar trees again (up to `MAX_EXEMPLARS` MCP calls, against `MAX_TOOL_CALLS` per run). If the diagnoser ever gets tools, move it to `create_agent(response_format=Diagnosis)` with a low recursion limit (~12). The outer pipeline stays a plain `StateGraph`.
- Parallel branches get small private inputs (`ClusterTask`, `ReproTask`), not the whole state. Fields filled by parallel branches use `Annotated[list[...], operator.add]`.
- Clustering is code (embeddings + HDBSCAN), not LLM calls. LLM calls happen per cluster, never per trace.
- Tracing stack is our own: Medas (OpenTelemetry, `gen_ai.*` attributes) → FastAPI OTLP collector → Postgres (`traces`, `spans`, `scores`) → FastMCP read-only server → graph. Decided: no third-party observability platform (no Langfuse). The Langfuse mentions in `tracedoctor_graph.py` are stale.

## Safety invariants

- Trace access is read-only: the MCP server (`search_failed_traces`, `get_trace_tree`, `get_span`) connects with a read-only Postgres role. The agent never touches the DB directly: `agent/` imports only `trace_store.models` and no DB drivers, and `backend/tests/test_boundaries.py` enforces it.
- MCP tool calls are limited where their arguments are declared and by one middleware. `search_failed_traces` serves only `ALLOWED_APPS` (checked in the tool body), and trace and span ids are typed `TraceId` (`models.py`, pattern `ID_PATTERN`), so pydantic rejects other shapes; give any new tool that takes an id the `TraceId` type. `TraceGuard` (`trace_store/guard.py`) wraps every call with a per-run budget (`MAX_TOOL_CALLS`; one server process is one graph run) and an audit log of tool, outcome and a hash of the arguments on stderr, never raw arguments, results or exception messages. Known limits: FastMCP's own "Invalid arguments for tool" warning repeats a rejected id or query on stderr, outside the guard's control; `get_trace_tree` and `get_span` take only ids, so they are not app-scoped until the Postgres reader does it.
- All writes (GitHub, eval dataset, known-issues store) happen only in `apply_actions`, only for human-approved proposals.
- `dry_run` defaults to `True` and is set by the server only (`DRY_RUN`), never by a request. Dry run writes `out/issues/<cluster>.md` and appends regression cases to `out/regression_cases.jsonl`, and nothing else (`out/` is `backend/out` when the app runs from `backend/`; it is gitignored and can hold the diagnoser's prose). Real writes do not exist yet: `DRY_RUN` off is refused at startup, and `apply_actions` refuses it too.
- The known-issues store is written only after an approved action, so rejected proposals never become "known".

## Commands

Backend commands run from `backend/`. This project uses `uv`, not `pip` (and `python3 -m venv` fails on this machine because `ensurepip` is missing). Create the virtualenv and install dependencies:

```bash
cd backend && uv sync
```

Run the FastAPI app (docs at `/docs`):

```bash
cd backend && uv run uvicorn main:app --reload
```

The app needs `DATABASE_URL` (for example `postgresql://user:pass@127.0.0.1:5432/tracescan`; `docker compose up -d` at the repo root starts one on port 5433) to checkpoint run state into Postgres and to record runs, and fails at startup without it or before the migration has run:

```bash
cd backend && uv run --env-file .env alembic upgrade head
```

After changing `db/models.py`, write the migration with `uv run --env-file .env alembic revision --autogenerate -m "..."` and read it before committing. To also run the Postgres test, set `TEST_DATABASE_URL`; the docker command is at the top of `backend/tests/test_persistence.py`.

`DRY_RUN` is optional and on by default; the app refuses to start with it off (see the safety invariants).

The diagnoser calls a model through OpenRouter: the app also fails at startup without `OPENROUTER_API_KEY`; optionally set `UI_SPEC_MODEL` (the small model that writes the UI spec of each streamed message; default `anthropic/claude-haiku-5.5` in `agent/const.py`, built into `app.state.ui_spec_model`) and `DIAGNOSER_MODEL` (an OpenRouter slug such as `anthropic/claude-sonnet-5-5`; default in `agent/const.py`). Tests never call a model. `langchain-openrouter` pulls in the `openrouter` SDK, which caps `pydantic<2.13`, so pydantic sits at 2.12 until that cap is lifted.

Run the graph sketch (needs `langgraph` 1.x, which `pyproject.toml` does not list yet; add it with `uv add langgraph`):

```bash
cd backend && uv run python tracedoctor_graph.py
```

It runs to the review pause, prints proposals, then resumes with decisions on the same `thread_id`.

Frontend commands run from `frontend/` (install with `npm install`):

```bash
cd frontend && npm run dev
```

`npm run build` builds, `npm run lint` runs Biome, `npx tsc --noEmit` typechecks, and `npm test` runs the unit tests of the pure modules in `lib/` with Node's built-in runner (no dependency; those modules import each other with `.ts` extensions, which `allowImportingTsExtensions` allows, so `node --test` can load them). The UI needs the backend running too; if ports 3000 or 8000 are taken, start the backend with `--port 8010` and the frontend with `BACKEND_URL=http://localhost:8010 npm run dev -- --port 3010`.

Regenerate the board and work-packages brief after editing `tools/board/*.js` (from the repo root):

```bash
node tools/board/build-board.js tracescan-board.html .claude/prds/tracescan.work-packages.md
```

Backend checks (run from `backend/`; the Backend CI workflow runs the first three):

```bash
cd backend && uv run ruff check . && uv run ruff format --check . && uv run pytest
```

`RUN_SLOW=1 uv run pytest -k fastembed` repeats the clustering check with the real embedding model; setup, cache location and offline use are in the README. Without `RUN_SLOW` that test is skipped, so CI never downloads the model. Likewise `RUN_LLM=1 OPENROUTER_API_KEY=... uv run pytest -k real_model` runs the diagnoser on the real model over the fixture clusters, and CI never calls a model.

`uv run ruff check --fix .` and `uv run ruff format .` fix what they report. Ruff is configured in `backend/pyproject.toml` (rules `E,F,I,UP,B`, line length 100).

## Conventions

- Python, Pydantic models for all structured output and state. Store plain dicts in state, or register the models module with the checkpoint serializer, to avoid the LangGraph serialization warning.
- Target layout: `backend/agent/` (graph, `mcp_client.py`, later `nodes/` and `evals/`) and `backend/trace_store/` (contracts, reader, MCP server, later the Postgres reader); run modules from `backend/`, e.g. `uv run python -m agent.graph`. Do not name a package `mcp/`: it would shadow the official `mcp` package that FastMCP imports; Next.js UI in `frontend/` (PLAN.md still says `ui/`).
- Failure categories: `retrieval_miss`, `tool_schema_error`, `context_overflow`, `prompt_regression`, `model_quality`, `infra_error`, plus MAST top-level `system_design`, `inter_agent_misalignment`, `task_verification`, and `unknown`.
- Frontend design system lives in `frontend/app/globals.css` (see the comment block there): dark navy surfaces with one electric blue accent (`primary`), and four status colors used for status only: `info` (under way; a lighter blue than `primary`), `warning` (waiting for a person, the only color that asks for action), `success` and `destructive`; a status that is nothing or was stopped by choice (idle, cancelled, aborted) is `muted-foreground`. Every status chip is `Chip` in `app/_components/chip.tsx` (one recipe per tone in `CHIP_TONE`, a mark per tone so color is never the only signal; the tone names are `StatusTone` in `lib/runs.ts`). Four type sizes via `type-h1` (24), `type-h2` (16), `type-h3` (14), `type-h4` (12 mono overline) plus `type-body` (14), and two weights (400, 500); do not use `text-xs`/`text-lg`/`text-3xl` or `font-semibold`. Desktop layout is a 12-column grid with body content on 9 columns (3/4).
- Eval = fault injection in Medas (6 seeded faults, varied inputs, healthy controls). Grade on the injected cause, not just the visible symptom.
- For parallel subagent work: contracts and fixtures first, one owner per path, stubs for neighbouring features. See `.claude/prds/tracescan.work-packages.md`.
